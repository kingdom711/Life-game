# 프론트엔드 진행현황 

> 프로젝트: 안전의 길 (Safety Quest Game)  
> 문서 목적: `공적 문제 해결 관점 + 바이브 코딩 실행 방식`으로 강사 피드백을 빠르게 받기 위한 요약본  
> 마지막 업데이트: 2026-04-08

---

## 1) 30초 요약

- 현재 프론트엔드는 **현장 안전행동을 일상화하는 MVP+ 단계**까지 구현됨
- 코드베이스 규모: `pages 35`, `components 48`, `api 21`, `utils 35`, `data 12`
- 핵심 플로우(가입/역할선택/퀘스트/보상/교환/교육/알림/위험분석)가 실제 화면/로직으로 존재
- 프로젝트 목표는 SaaS 매출보다 **산업안전 공적 문제 해결(참여율, 실천율, 사고예방 기여)**에 있음

---

## 2) 문제정의와 접근 방식

### 해결하려는 공적 문제
- 기존 집합 안전교육은 교육 효과 대비 현장 업무 공백이 크고, 참여 동기 유지가 어려움
- 교육/점검/보상이 분리되어 안전행동이 일회성으로 끝나는 문제가 있음

### 현재 접근
- 매일 짧게 실행 가능한 마이크로 안전활동(퀘스트/교육/점검)을 제공
- 게임화 보상(레벨/아이템/포인트)으로 참여를 습관화
- AI 위험분석/알림/작업중지 기능으로 현장 대응성과 기록성을 강화

## 3) 사용자 흐름 기준 현재 상태

| 사용자 여정 | 상태 | 메모 |
|---|---|---|
| 회원가입/로그인/역할선택 | 완료 | 관리자 ID 로그인 포함 |
| 대시보드/일·주·월 퀘스트 | 완료 | 반복 참여 루프 구현 |
| 보상체계(상점/인벤토리/교환/보상센터) | 완료 | 동기부여 루프 구현 |
| 교육(영상 누적/퀴즈) | 완료 | 시청시간 기반 진행 제어 |
| 안전기능(AI 위험분석/알림/작업중지) | 완료 | 화면 및 플로우 구현 |
| 운영 고도화(성과지표/자동테스트/정책 운영) | 보완 필요 | 확산 단계 준비 영역 |

## 4) 지속가능성 모델: 절약된 시간이 보상이 됩니다

기존 집합 안전교육은 사업장에 교육비 외 추가 손실을 유발합니다.  
월 1회 정기안전교육(2시간) + 이동/복귀(1시간) 기준, 근로자 1인당 회당 약 3시간의 업무 공백이 발생합니다.

| 항목 | 내용 |
|---|---|
| 교육 1회당 업무 공백 | 교육 2시간 + 이동 왕복 1시간 = 3시간/인 |
| 연간 손실 시간(1인) | 3시간 × 12회 = 36시간 |
| 연간 인건비 손실(1인) | 36시간 × 18,000원 = 648,000원 |
| 50인 사업장 기준 | 648,000원 × 50인 = 연간 약 3,240만 원 |

### 환류 구조
- 기존 “모여서 교육” 시간 일부를 `업무 시작 전 10분형 마이크로 학습`으로 전환
- 이동·대기·집합 비용을 절감하고, 절감된 자원을
  `프로젝트 운영비 + 참여자 보상(포인트/인센티브)`으로 재투입
- 결과적으로 외부 지원 의존이 아닌 **현장 내부의 시간·비용 재배치**로 지속가능성 확보

## 5) 강사 피드백 요청 항목 (핵심)

1. 현재 구성에서 공적 문제 해결 효과를 입증하려면, 어떤 성과지표(참여율/완료율/행동변화/사고지표)를 우선 측정해야 하는지
2. “10분형 안전활동” 모델이 현장에 안착하도록 UX/운영 측면에서 보완할 우선순위
3. 바이브 코딩 속도를 유지하면서도 품질(회귀 방지, 로그, 테스트) 확보를 위한 최소 개발 루틴
4. 교육 이수 인정 조건으로서, `교육 결과 데이터의 사후 수정 불가(또는 수정 이력 완전 추적)`를 어떤 수준으로 증명해야 실무/심사에서 신뢰받을 수 있는지

### 5-1) 교육 결과 무결성 증명(피드백 요청안)

- 핵심 쟁점: 교육으로 인정받으려면 "저장됨"보다 "위변조가 어렵고, 시도 시 추적 가능함"을 증명해야 함
- 검토 요청: 아래 최소 증빙 세트로 충분한지 강사 검토 필요

| 증빙 항목 | 확인 포인트 |
|---|---|
| DB/저장 구조 | 교육 결과는 append-only(수정/삭제 금지), 정정은 신규 레코드로만 처리 |
| API 정책 | 결과 저장은 생성(POST) 중심, 임의 수정 API 비활성 또는 관리자 승인형 |
| 감사 로그 | 누가/언제/무엇을 변경 시도했는지 별도 audit_log에 기록 |
| 무결성 값 | record_hash(+ 필요 시 prev_hash 체인) 저장 및 검증 가능 |
| 시간 기준 | 서버 시간(created_at) 기준으로만 이수 판정 |
| 권한 통제 | 운영자/관리자 권한 분리 및 정정 승인 절차 |

### 5-2) 시연/제출 방식 (예정)

1. 교육 완료 이벤트 저장 확인(사용자, 콘텐츠, 시간, 결과)
2. 사후 수정 시도 실패 또는 정정 이력 추가 방식 시연
3. 감사 로그 및 해시 검증 결과 제시(PASS/FAIL)
4. 최종적으로 "이수 인정 가능 데이터"와 "참고용 데이터" 구분 기준 설명

## 6) 데모 시나리오 (5~7분 권장)

1. 로그인/역할선택 → 대시보드 진입
2. 퀘스트 수행 및 보상 획득
3. 상점/인벤토리/교환/보상센터로 참여 동기 루프 시연
4. 교육(시청 누적) + AI 위험분석 + 알림/작업중지 시연
5. 마지막 1분: “절약 시간 환류 기반 지속가능성” 설명 및 질의
